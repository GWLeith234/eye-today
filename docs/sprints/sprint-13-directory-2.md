# Sprint 13 — Directory II — claims, featured listings & map

**Goal:** Listing owners can prove they run a listing and propose corrections, a listing can be featured (paid, labelled) through Stripe, and readers can see results on a map.

Depends on PR #13 (Sprint 12): `supabase/migrations/0013_directory.sql` is on `main`. Branch: `sprint-13-directory-2`. Migration: `0014_directory_claims.sql` only.

**Definition of done:** Claim a listing with a domain email → propose an edit → editor approves; buy a featured listing in Stripe test mode → it shows as Featured at the top of its filtered results → cancel → it stops being featured at period end; map view shows the same results as the list.

**Won't change:** verification rules, reviews or ratings, the description claims check, `RESERVED_SECTION_SLUGS` (`directory` is already reserved; the map is `?view=map`).

## How it is built

- **Claims.** `request_listing_claim` (signed in, rate limited) accepts only an email whose domain equals the listing website's host (with or without `www.`). The one-time code is generated by the server, stored as `sha256`, and emailed with `sendMail`. The code hash is written by `set_listing_claim_code`, which only the service role can run: if a user could choose the hash, they could skip the email proof. That is the single service-role call in the claims flow. Every other action uses the user-scoped client. `confirm_listing_claim` answers true or false and never says which check failed; five wrong codes expire the claim.
- **Owner edits never change verification.** `propose_listing_edit` keeps only a whitelist of keys; `approve_listing_proposal` (editors only) writes only those columns. It never touches `verification_level`, `verification_note`, `status`, `relationship_disclosure`, `lat` or `lng`. A SQL test and a unit test both feed a payload that includes `verification_level`.
- **Featured.** Stripe Checkout (subscription) with `metadata.kind = directory_feature`. `handleStripeEvent` upserts `listing_features` and returns before any membership logic. The public query counts a feature only while `status = 'active'` and `current_period_end > now()`. Page 1 pins at most 3 featured matches, then organic rows; later pages are the same ordering at the next offset, so nothing repeats or is skipped, and each listing appears once.
- **Map.** `?view=map` on `/directory`. Leaflet 1.9.4, react-leaflet 5, leaflet.markercluster in a client component loaded with `ssr: false`. OSM tiles with attribution. The list always renders too, so the map and list show the same names.
- **Story links, reports, newsletter.** Editors attach listings to articles; listing pages show related stories; every listing has a "Report a problem" form (Turnstile, rate limit, `report_listing`); a newsletter issue can append "New in the directory".

## Env (server only)

`STRIPE_PRICE_FEATURED_MONTHLY`, `STRIPE_PRICE_FEATURED_ANNUAL`. With either price id, `STRIPE_SECRET_KEY` or `SITE_URL` missing, featured checkout is not offered.
